# 賞味期限管理

バーコードを読んで賞味期限を登録し、期限が近いものを毎朝 9:00（JST）に Slack へ流す。
通知は **7日前・3日前・前日** の3回。DB は Google スプレッドシート。

読んだ JAN が商品DBに無ければ、その場で商品名と属性を入力して登録する。
入力した商品はDBにも足されるので、次に同じ商品を読んだときは名前が出る。

担当者が画面でするのは**自分の名前を選ぶ**ことだけ。接続先とパスコードは
`docs/config.js` に固定してあり、担当者は触らない。

セットアップ手順は **[SETUP.md](SETUP.md)** にある。ここには「なぜこの作りなのか」を書く。

---

## 全体像

```
  スマホ / PC のブラウザ
  ┌──────────────────────────┐
  │ 画面（GitHub Pages・HTTPS）      │   カメラ・USBリーダー・手入力
  │  docs/index.html app.js config.js │
  └──────────┬───────────────┘
             │ POST（JSON）
             ▼
  ┌──────────────────────────┐
  │ GAS ウェブアプリ（JSON API）      │──▶ JANコードDB（Yahoo/楽天/OpenFoodFacts）
  │  gas/Code.gs  gas/Jan.gs         │
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │ スプレッドシート                  │
  │  登録シート／DBシート／ログ        │
  └──────────┬───────────────┘
             │ POST（action=due・読み取りのみ）
             ▼
  ┌──────────────────────────┐
  │ GitHub Actions（毎朝 9:00 JST）   │──▶ Slack
  │  .github/scripts/notify.mjs      │
  └──────────────────────────┘
```

インストールするものは無い。担当者に渡すのは **画面のURL 1つだけ**。
接続先とパスコードは `docs/config.js` に入っていて、画面と一緒に配信される。

## 設計の理由

### 画面を GAS ではなく GitHub Pages に置いた

これが一番大きな判断で、**実測ではなく既知の制約から決めた**。

GAS のウェブアプリは sandboxed iframe（opaque origin）の中で描画される。
ブラウザは opaque origin からのカメラ要求を、利用者が「許可」を押しても拒否する。
Apps Script 側の設定では回避できない（`sandbox` に `allow-camera` は無い）。

つまり **GAS の画面にバーコードスキャナは載せられない**。
そこで画面を GitHub Pages（最上位の HTTPS ページ）に出し、GAS は JSON API に徹させた。

副次的に、こちらの方が運用も楽だった。

- 画面の更新が `git push` だけで反映される（GAS への貼り直しが要らない）
- スマホでもPCでも同じ1つの画面で済む
- GitHub Actions を使う以上リポジトリは必要なので、Pages は追加コストゼロ

### 接続先とパスコードは config.js に固定し、聞くのは「作業する人」だけ

書き込み先のスプレッドシートは基本的に変わらない。にもかかわらず担当者ごと・端末ごとに
URL とパスコードを入力させると、打ち間違い・古い値の残留・端末ごとの食い違いが起きる。
GASを再デプロイして `/exec` の URL が変わったときに、全員に入力し直してもらうのも現実的でない。

なので接続先は `docs/config.js` の1か所に置いた。ここを直して push すれば全員に効く。
担当者側の操作は要らない。設定ダイアログからは**変えられない**ようにしてある
（端末ごとにバラバラの接続先が残ると、原因の分からない不一致になるため）。

**引き換えに何を諦めたか（承知の上）:**
GitHub Pages を無料で使うにはリポジトリが public になるので、
`config.js` のパスコードは**ページを開ける人・リポジトリを見られる人には見える**。
つまりパスコードは「部外者が偶然たどり着かない」程度の鍵であって、秘密ではない。
シートに人に見せられないものは置かないこと。漏れたときはメニュー
「② パスコードを設定する」で変えて `config.js` も直す（2か所を同時に変える）。

`config.js` の url / pass を両方空にしておくと、画面は今まで通り
「接続URL・パスコードを入力する画面」を出す。別のスプレッドシートで試すときの逃げ道として残してある。

### 「作業する人」は毎回聞き、保存しない

現場の端末は共用のことがある。前に使った人の名前が残っていると、
ログに別人の名前が積まれる。**画面を開くたびに名前を聞く。**

とはいえ毎回フルネームを打たせるのは現場では続かないので、
一度使った名前は候補ボタンとして残し、1タップで選べるようにした
（保存しているのは候補リストだけで、「今誰が作業中か」は保存していない）。
候補は最近使った順に最大8件、それぞれの ✕ で消せる。
途中で交代するときは 設定 →「人を変える」。

### JANコードDB の照会をサーバー側でやっている

ブラウザから Yahoo!ショッピングAPI 等を直接叩くと、

1. CORS で失敗する
2. APIキーが public なソースに載る

の両方で駄目になる。GAS の `UrlFetchApp` から叩き、キーはスクリプト プロパティに置いた。

取得した商品名は**確定ではなく候補**として扱う。画面では編集可能な入力欄に入れるだけで、
人が確認して「登録する」を押すまでシートには入らない。通販サイトの商品名は
`【送料無料】…まとめ買い` のような販促文が混ざるので、目立つ分だけ機械的に落としている
（`cleanName_`）。それでも人が直す前提。

キーが未設定のサービスは、理由を付けてスキップするだけで他を止めない。
キーを1つも設定しなくても、Open Food Facts（キー不要）と手入力で運用できる。

### 利用者のシートに合わせ、書き込むのは A列と D列だけにした

登録シートは利用者が先に作っていたもので、`A:JAN B:商品名 C:属性 D:賞味期限` の4列。
アプリが書くのは **A列（JAN）と D列（賞味期限）** だけで、1回の登録ごとに1行足す。

B列・C列に触らないのは、そこが DBシートを引く**数式のことがある**ため。
数式のセルに値を書くと `#REF!` が広がって、人が直すまで表が読めなくなる。
ただし数式が入っていないシートだと、書かなければ商品名が空の行が残って人が読めない。
そこで「その列に数式が1つも無く、かつ書き込む先が空のとき」だけ商品名と属性も入れる
（`fillIfPlainColumn_`）。どちらの作りのシートでも壊れず、目で読める形になる。

一覧の商品名と属性は、登録シートの B・C ではなく**DBシートから引き直している**。
そうすると B・C が数式でも値でも空でも、同じ結果になる。

### 一覧は読み取り専用にした

登録シートには行を一意に指せるID列が無い（利用者のシートに合わせて4列のままにした）。
行番号で書き換えると、誰かがシートに1行挿入した瞬間に別の行を壊す。
当てずっぽうで叩かないために、画面から特定の行を書き換える操作は**用意していない**。
数量・状態（消費済み／破棄）・担当者の列も無いので、その機能も持たない。
直したいときはスプレッドシートを直接開く。誰が・いつ・何を登録したかは `ログ` シートに残る。

### 掴んだシートが違っていたら、書かずに止める

登録シートとDBシートは **gid**（シートURLの `#gid=` の数字）で特定している。
シート名を変えても gid は変わらないので、名前より壊れにくい。

そのうえで、書き込む前に A1 が「JAN」かどうかを確かめる（`resolveSheet_`）。
違えばエラーにして何も書かない。**関係ないシートに書き込むのがいちばん怖い**ため。
別のスプレッドシートで使うときは、メニュー「使うシートを指定する」で
`REGISTER_SHEET` / `DB_SHEET`（シート名でも gid でもよい）を上書きする。

### 通知を GAS のトリガーではなく GitHub Actions にした

GAS には時限トリガーがあるので通知だけなら GAS だけで完結する。
それでも Actions にしたのは、

- 実行ログが残り、失敗したことに気づける（GAS のトリガー失敗は静かに埋もれる）
- 手動実行で **DRY-RUN**（Slack に送らず内容だけ確認）ができる
- Slack の Webhook URL を GitHub Secrets に置ける

GAS 側は `action=due` で読み取るだけ。この経路がデータを書き換えることはない。

### 通知は「以内」ではなく「ちょうどその日」で拾う

通知の設定と画面の設定は**別物**にしてある。混ぜると片方を直したときにもう片方が壊れる。

| | 設定 | 既定 | 効くところ |
|---|---|---|---|
| 通知 | `NOTIFY_DAYS` | `1,3,7` | Slack。期限まで**ちょうど**その日数のものだけ |
| 画面 | `SOON_DAYS` | `7` | 一覧の色分け。あと7日**以内**で色が付く |

通知を「7日以内」にすると、同じ商品が7日連続で通知に載る。毎日同じものが並ぶ通知は
読まれなくなるので、**7日前・3日前・前日の3回だけ**流す形にした。

代わりに副作用が1つある。**その日の実行が失敗すると、その商品のその回の通知は永久に来ない**
（「以内」なら翌日に取り返せた）。3回に分散させてあるので全部落ちる確率は低いが、
Actions が失敗したら気づけるように、通知の取得に失敗したときは**異常終了**させている
（黙って「0件」として正常終了しない）。

期限切れだけは例外で、日数にかかわらず毎回載せる。放置された在庫を通知から外すと、
誰も気づかないまま残り続けるため。通知から落としたいときは、
登録シートのその行を消すか、賞味期限を空にする。

画面側では `SOON_DAYS` 以内になると行に色が付く。それより先のものは色を付けず、
灰色で残り日数だけ出している（列の意味が「期限まで」なので、
空欄にするより並べ替えたときに分かりやすい）。

## シートの構成

| シート | 既定の gid | 列 | アプリが書くところ |
|---|---|---|---|
| 登録シート | `0` | A:JAN / B:商品名 / C:属性 / D:賞味期限 | **A と D**（＋B・Cが数式でないときだけ B・C も） |
| DBシート | `391546061` | A:JAN / B:商品名 / C:属性 | 未知のJANのとき末尾に1行 |
| `ログ` | （自動作成） | 日時 / 操作 / 対象行 / 内容 / 担当者 | 毎回1行 |

- **列の位置は固定**（`COL`）。利用者のシートのレイアウトに合わせてある。
  列を挿入するとずれるので、挿入しないこと。1行目の見出しは変えてよいが、A1 は「JAN」を含む必要がある。
- **登録は毎回1行追加**。同じ商品を別の期限で何度でも登録できる。既存の行は書き換えない。
- 登録シートには**賞味期限が空の行**が混ざる（商品リストを貼っただけの行。最初から135行ある）。
  一覧では既定で表示せず、件数だけ知らせる。「すべて」を選ぶと出る。通知には載らない。
- JANコード列は書く前に文字列書式にしている。数値のままだと 13桁が `4.9012E+12` になる。
  読むときも `normJan_` で数値・ハイフン入りのどちらでも受ける。
- 賞味期限は `2026/9/1` や `2026年9月1日` と手で書いても読み取れる（`normYMD_`）。
- **属性は自由入力**。選択肢を固定していないので、新しい属性をその場で作れる。
  表記がばらけると絞り込みが効かなくなるので、入力欄の下に「すでに使われている属性」を出している。

## 安全装置

| | |
|---|---|
| 外部への送信 | Slack 通知は、手動実行では既定で **DRY-RUN**。定期実行のみ実送信する |
| 読み取り | DRY-RUN でも GAS からは**本物のデータ**を読む。偽データにすると対象確認ができず、かえって危ない |
| 書き込む先の確認 | 掴んだシートの A1 が「JAN」でなければ**何も書かずにエラー**（関係ないシートを触らない） |
| 数式の列 | B・C列に数式があれば書き込まない（`#REF!` を撒かない） |
| 既存の行 | 書き換えない。登録は必ず末尾に1行追加 |
| 同時書き込み | `LockService` で直列化。末尾追加なので取り合いにならない |
| 認証 | パスコード未設定なら**全拒否**（開けっ放しにしない）。`ping` だけ疎通確認のため素通し |
| パスコードの置き場 | `config.js`（画面と一緒に配信される＝実質公開）。**部外者が偶然たどり着かないための鍵**であって秘密ではない。見せられないものをシートに置かない |
| 誰が登録したか | 画面を開くたびに名前を聞き、保存しない。前の人の名前でログが積まれないようにする |
| 接続先の変更 | 担当者の画面からは変えられない。`config.js` を直して push（1か所）|
| 商品名の扱い | 外部由来の文字列は DOM API で組み立て、Slack へは mrkdwn をエスケープして送る |
| 外部DBの商品名 | 自動では欄に入れない。候補ボタンを押して初めて入る（通販サイトの名前は実物と違うことがある） |
| 失敗の扱い | 通知は1件でも取得に失敗したら異常終了する（黙って0件通知にしない）。件数超過で省略したときは通知にその旨を書く |

| `tests/notify.test.mjs` | 14 | 通知スクリプトを、GAS と Slack の代わりの偽サーバー相手に実行する |

## 実測で分かったこと（推測と分けて書く）

**実測した:**

- 上の104件のテストは全て実行して通した（2026-09-04 に実行）。
- 賞味期限が空の行が「あと7日以内」に数えられるバグがあり、画面テストで見つけて直した。
  JavaScript では `null >= 0` が `true` になるのが原因。`daysLeft !== null` を明示している。
- テストの「今日」を `todayYMD_()` の差し替えだけで固定すると、**書いた日の翌日から壊れる**。
  登録日時・更新日時・ログは GAS 側が `new Date()` で直接書いているので、そこだけ本物の時計が残るため。
  実際 2026-08-27 に書いたテストが 09-03 に落ちた。引数なしの `new Date()` だけを固定日時にする
  `FixedDate` に差し替え、`ymdToDate_` が使う `new Date(y, m, d)` と `Date.UTC` は本物のまま残している。
- PowerShell 5.1 で native exe に `2>$null` を付けると `NativeCommandError` になり、
  `$ErrorActionPreference = 'Stop'` と併せて落ちる。`Start-Process -RedirectStandardError` に変えた。
- このPCではポート 5062 を既存の Flask アプリが使っていた。テストは 5058 を使う。
- **非表示の `<input type="url">` に不正な値が残っていると、`<form method="dialog">` の
  送信がブラウザに黙って止められる。** 設定ダイアログの「保存」が無反応になった
  （画面には何も出ない）。隠していても制約検証は効くため。`novalidate` を付け、
  さらに保存・人を変えるは `type="button"` にして押した時点で処理するようにした。
- **`dialog` の `close` イベント待ちで副作用を起こすと、ヘッドレステストで取りこぼす。**
  仮想時間で走らせると `close` の配送順が揺れ、同じテストが通ったり落ちたりした。
  ボタンのクリックで同期的に処理する形にしたら安定した（実ブラウザでも、
  Esc で閉じたときは何も起きない＝取り消し、と挙動がはっきりする）。
- 利用者のスプレッドシートを実際に読んで列構成を確かめた（推測ではない）。
  登録シート（gid 0）は `JAN / 商品名 / 属性 / 賞味期限` の4列・約135行で、賞味期限は全行空。
  DBシート（gid 391546061）は `JAN / 商品名 / 属性` の3列・約135件で、属性は「食品」と「駄菓子」の2種類。
  JANは8桁のもの（`49480795` など）も混ざっている。桁数で弾いてはいけない。

- **ZXing の動画用ループ（`decodeFromStream` / `decodeFromVideoDevice`）はそのままでは読めない。**
  カメラは起動し、映像も出て、デコードのループも回っている（6秒で32回）のに、一度も読めなかった。
  原因は、動画から取ったフレームに対してライブラリが `doAutoInvert = true` を強制すること。
  この指定は輝度を**1枚おきに白黒反転**させる（内部の静的フラグ `FRAME_INDEX` を毎回反転する）。
  実測すると、同じ1枚を `autoInvert=false` なら4回中4回読めるのに、`true` だと交互に落ちる。
  こちらの呼び方では反転側に張り付いていた。
  **ライブラリの動画ループは使わず、自前で「video を canvas に写して1枚読む」形にした。**
  1280×720 で1回 6.6ms なので、120ms 間隔でも余裕がある。
  この事故は「カメラは動いているように見える」ので、見た目では気づけない。
  生成したバーコードを偽のカメラ映像として流すテストを常設にしてある。
- **Windows では、他のアプリ・他のタブがカメラを掴んでいると開けない**（`NotReadableError`）。
  実際に Chrome が掴んだままで Edge から開けなかった。
  誰が掴んでいるかは
  `HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\CapabilityAccessManager\ConsentStore\webcam`
  の `LastUsedTimeStop = 0` で分かる。
  画面を離れたらカメラを離すようにし、エラーは日本語で「他のアプリかタブが使っています」と出す。
- **`--virtual-time-budget` を使ったヘッドレステストでは `getUserMedia` が間に合わない。**
  時計を飛ばすので、カメラが開く前にテストが終わる。`dialog` の `close` イベントの配送順も
  揺れて、同じテストが通ったり落ちたりした。仮想時間をやめ、テストが終わるまで
  画面側が `load` イベントを止めておく形にした（サーバーの `/wait` が応答しないことを利用する）。
- このPCのカメラは1台（`FJ Camera`）で、1920×1080 が取れる。

**まだ実測していない（実機・実デプロイが要る）:**

- **スマホ実機でのカメラ読み取り。** Android Chrome は `BarcodeDetector`、
  iOS Safari は非対応なので同梱の ZXing に切り替わる実装にしてあるが、どちらも実機では試していない。
  PC では**生成したバーコードなら確実に読める**ところまで確認済み。
  ただし現物の印刷バーコードを内蔵カメラ（固定焦点）で読めるかは別問題。
- **現物のバーコードでの読み取り成功率。** 合成した完全なバーコードは読めるが、
  印刷のかすれ・光の反射・ピンぼけがどれだけ効くかは実物でしか分からない。
- **GAS への `fetch` が CORS を通るか。** `Content-Type: text/plain` にしてプリフライトを
  回避する定番の方法を使っているが、実デプロイでは未検証。
  もし失敗するなら、ブラウザのコンソールに CORS のエラーが出る。
- **JANコードDB のヒット率。** Open Food Facts は食品向けだが日本の商品カバレッジは薄い。
  実運用では Yahoo! か楽天のキーを設定した方が当たると思われる（未検証）。
- **GitHub Actions の cron の実際のずれ。** 混雑時は数分〜数十分遅れる（GitHubの仕様）。
- **登録シートの B・C列が数式なのか、ただの値なのか。** スプレッドシートを読んでも
  計算結果しか見えないので判別できていない。どちらでも壊れないようにしてある
  （数式があれば触らない／無ければ値を入れる）が、**最初の1件を登録したら
  シートを目で見て、商品名と属性が入っているか確かめること**。
  もし B列が `=ARRAYFORMULA(...)` で、その式が新しい行に対して空文字を返す作りだと、
  「数式が無い」と誤判定して値を書き込む可能性がある（この場合だけ数式が1つ壊れる）。

## まだやっていないこと

- **LINE 通知。** 今回は Slack のみ。LINE Notify は 2025年3月末で終了しているので、
  やるなら LINE Messaging API（公式アカウント＋チャネルアクセストークン）が必要になる。
  `notify.mjs` の `postToSlack` と同じ形で送信先を足せば載せられる。
- **画面から登録済みの行を直す・消す。** 登録シートに行を一意に指せるID列が無いので付けていない。
  やるなら「行番号＋その行のJANと期限が画面で見たものと一致すること」を確かめてから
  書き換える形にする（行が挿入されていたら触らない）。
- **数量。** 登録シートに数量の列が無いので持っていない。同じ商品が3個あるなら3回登録する。
- **消費済み・破棄の記録。** 状態の列が無いので、消費したものは登録シートから消すことになる。
- **賞味期限の写真からの OCR。** 手打ちとカレンダー選択のみ。
- **通知先の出し分け**（担当者ごと・拠点ごと）。今は1つのチャンネルに全件送る。
- **DBシートの商品名を直したときの登録シートへの反映。** 一覧はDBシートから引き直すので
  画面上は直った名前が出るが、登録シートの B列に値が入っている場合、その値は古いまま残る。
- **属性の表記ゆれの統合。** 自由入力なので「食品」と「食 品」が別物になる。
  入力欄の下に既存の属性を出しているだけで、強制はしていない。
- **登録内容の CSV 書き出し。** スプレッドシートを直接見れば済むので省いた。

## 困ったとき

| 症状 | 見るところ |
|---|---|
| 画面が真っ白 / 一部が出ない | ブラウザの開発者ツールのコンソール。`tests\e2e\run.ps1` でも再現するか確認する |
| 「接続できません」 | 接続URLが `/exec` で終わっているか。GASを再デプロイしたらURLが変わっていないか |
| 「パスコードが違います」 | `docs/config.js` の `pass` と、シートのメニュー「賞味期限管理 → 接続情報を表示する」の先頭2文字が一致しているか確認する |
| 「接続先に繋がりません」と名前の画面に出る | `docs/config.js` の `url` が古い（GASを再デプロイするとURLが変わる）。直して push する |
| 接続URLの入力画面が出る | `docs/config.js` の url / pass が空。入れて push する |
| 前の人の名前で登録されてしまう | 起きないはず（毎回聞く）。設定 →「人を変える」でも切り替えられる |
| カメラが起動しない | 画面に出る文言を見る。「他のアプリかタブが使っています」なら Teams・Zoom・別のタブを閉じる（Windowsはカメラを1つのアプリでしか使えない）。「許可されていません」ならアドレスバーのカメラのアイコンから許可する |
| カメラは映るが読めない | 映像の下に出る `（ZXing / 1920×1080 / カメラ名）` を確認する。解像度が低い/別のカメラなら、下の一覧で選び直す。ノートPCの内蔵カメラは固定焦点なので 25〜30cm 離し、バーコードが画面幅の半分以上になるように構える |
| 商品名が自動で入らない | メニュー「JANコードDBのAPIキーを設定する」で設定状況を確認。未設定でも手入力で登録できる |
| Slack に来ない | Actions の実行ログ。`dry_run: true` のまま手動実行していないか。Secrets が揃っているか |
| 通知に載るはずの商品が来ない | 賞味期限までが**ちょうど** 7 / 3 / 1 日か確認する。5日後などは通知されない（仕様）。メニュー「通知する日を変える」で増やせる |
| JANが `4.9012E+12` になる | メニュー「① シートを作る / 整える」を実行し直す（列を文字列書式に戻す） |
